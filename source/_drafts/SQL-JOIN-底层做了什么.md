MySQL 的 JOIN 不是由 InnoDB 等存储引擎实现的，而是在Server 层由查询优化器执行的；优化器会先遵循小表驱动大表原则选择驱动表（外层循环表）和被驱动表（内层循环表），目的是减少外层循环的次数；另外会用到join buffer（连接缓冲区，由join_buffer_size控制）做内存优化，这是 BNLJ、Hash Join 的核心依赖。

* 如果JOIN ON的键在被驱动的小表没有命中索引可能性能很差

* 可以使用STRAIGHT_JOIN强制指定连接顺序：users STRAIGHT_JOIN orders （users是驱动表）

### 哪些join算法

#### 一、嵌套循环连接：Nested Loop Join（NLJ）

有命中索引：O(M*logN)

没有命中索引：O(M*N)

因为是「逐行取、逐行匹配、匹配完释放」，仅需存储驱动表的单行数据和连接键，空间复杂度与被驱动表大小相关 O(N)

### 二、块嵌套循环连接：Block Nested Loop Join（BNLJ）

对无索引全表扫描的优化。MySQL8.0 之前，无索引 JOIN 的默认算法。

将「驱动表每行扫描一次被驱动表」升级为「驱动表每块扫描一次被驱动表」，总时间复杂度 O(k∗N)（k = M/block_length 为驱动表分块数）。

### 三、哈希连接：Hash Join（MySQL8.0 + 正式支持，核心优化）

「建哈希表 + 哈希探测」，利用哈希表的O (1) 平均查找特性，将双层循环的乘法复杂度降为加法复杂度。

构建哈希表：遍历驱动表O(M)，哈希计算是O(1)平均时间，总O(M)；

哈希探测：遍历被驱动表O(N)，每次哈希查找O(1)平均时间，总O(N)；

理论总时间复杂度：O(M+N)

若驱动表过大，内存装不下哈希表，优化器会将哈希表分桶存储到磁盘，执行时逐桶加载到内存匹配，此时时间复杂度会上升为`O(M/k*k*N)`（k为分桶数），但仍远优于 BNLJ；

### 能不能不Join？

1.反范式化设计，新增冗余字段，异步更新

2.中间件分别查询，在应用层合并

3.使用联合索引避免JOIN

4.上缓存：读到结果缓存，写则删除缓存
